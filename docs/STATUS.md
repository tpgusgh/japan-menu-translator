# 현재 상태 정리

일본 메뉴/간판 번역 앱 — 지금까지 구현된 것, 알려진 한계, 개선하려면 뭐가 필요한지 정리.

## 아키텍처 요약

```
[카메라 촬영]
      ↓
[modules/ml-features (Kotlin 네이티브 모듈)]
  - recognizeText   : ML Kit Text Recognition (일본어) — OCR
  - isModelDownloaded/downloadModel/translateText : ML Kit Translate (ja↔ko, 온디바이스)
  - getReadings     : kuromoji-ipadic (일본어 형태소 분석, 한자 읽기 추출)
      ↓
[src/lib/*.ts]
  - ocr.ts        : OCR 결과에서 가격줄·비일본어 잡음 필터링
  - translate.ts  : 번역 래퍼
  - pronounce.ts  : 읽기(가나) → 한글 발음 변환 (kana-to-hangul.ts, 순수 함수)
  - wikipedia.ts  : 온라인일 때만 위키백과 요약 fetch (설명 보기 눌렀을 때 지연 호출)
      ↓
[src/screens/ScanScreen.tsx]
  - 카메라 미리보기 + 확대 버튼 → 촬영 → OCR → 번역+발음 병렬 처리 → 사진 위 오버레이 + 카드 리스트
[src/screens/ReverseScreen.tsx]
  - 한국어 입력 → 일본어 번역 + 한글 발음
[src/screens/DownloadScreen.tsx]
  - 최초 실행시 ja/ko 번역 언어팩 다운로드 (이후 완전 오프라인)
```

서버/백엔드 없음. 로그인 없음. 위키백과 fetch 딱 하나만 외부 네트워크 호출(그것도 사용자가 "설명 보기" 눌렀을 때만).

## 핵심 설계 결정

- **OCR·번역·발음 전부 온디바이스(오프라인)**: 커뮤니티 npm 래퍼(`@react-native-ml-kit/*`)가 alpha 품질이라, ML Kit Android SDK를 Kotlin으로 직접 감싸는 커스텀 네이티브 모듈을 만듦. 장점: 완전 오프라인, 무료. 단점: OCR 정확도가 Google Cloud Vision 같은 클라우드 OCR보다 낮음(아래 한계 참고), 튜닝 여지 거의 없음(공개 API가 파라미터를 거의 안 열어줌).
- **가나→한글 발음은 자체 구현 근사 알고리즘**: 국립국어원 표기법 근사치. 완벽하지 않음(예: 촉음/장음 처리가 단순화됨).

## 지금까지 실사용 테스트에서 드러난 한계

1. **붓글씨/서예체 간판 인식 거의 안 됨.** ML Kit Japanese Text Recognizer는 인쇄체엔 강하지만 스타일라이즈된 필기체·목판 서예체는 잘 못 읽음. 코드로 고칠 수 있는 부분이 아니고(모델 자체 한계, 구글 번역 카메라도 동일), 인쇄된/각진 활자체 메뉴판이면 훨씬 잘 될 것으로 예상되지만 아직 실제 인쇄 메뉴판으로는 테스트 못함.
2. **작은 글씨/먼 거리 촬영 시 인식 실패.** 텍스트가 사진에서 일정 픽셀 크기 이하면 OCR이 아예 못 잡음. 완화책으로 수동 확대 버튼(+/-) 추가함. 근본적으로는 사용자가 항목에 가까이서 찍어야 함.
3. **번역 품질이 ML Kit Translate 자체 수준에 묶여 있음.** 흔한 음식명(寿司, 豚肉 등)은 잘 되지만, OCR이 애매하게 읽은 문자열(예: 카타카나 오독)은 번역도 같이 이상하게 나옴 — garbage in, garbage out.
4. **디자인은 "기능 우선" 최소 스타일 그대로.** 색상 팔레트, 타이포그래피, 여백, 로딩/에러 상태 트랜지션 등 시각 디자인 다듬은 적 없음. 사진 위 오버레이 말풍선은 텍스트 박스가 조밀하면 겹칠 수 있음(카드 리스트가 실제 가독성 있는 화면).

## OCR·번역을 더 개선하려면 필요한 것

### 선택지 A — 실제 테스트 자료로 현재 파이프라인 한계 더 정확히 파악
- 실제 인쇄된 일본 메뉴판/간판 사진 몇 장 (다양한 폰트/조명/각도) 주시면, 어디까지 되고 어디서 깨지는지 정확히 확인 후 그에 맞춰 필터/전처리 튜닝 가능. **비용 없음, API 키 필요 없음.**

### 선택지 B — 클라우드 OCR/번역 API로 교체(또는 병행)
정확도는 확실히 오름(특히 필기체·저화질), 대신 **오프라인 우선 설계 원칙과 정면으로 충돌**함 — 인터넷 없으면 아예 동작 안 하게 되거나, 온디바이스/클라우드 이중 경로를 만들어야 함(구현 복잡도 증가). 후보:
- **Google Cloud Vision API** (OCR) — 정확도 좋음, 종량제 과금, API 키 필요.
- **Naver Clova OCR / Papago** — 한국어 특화, 일본어 메뉴 인식·번역 품질이 ML Kit보다 나을 가능성 높음(특히 번역 자연스러움). API 키 + 네이버클라우드플랫폼 계정 필요, 종량제.
- **Upstage Document AI** 등 — 문서/메뉴판 특화 OCR 옵션도 있음.

이 옵션 쓰려면: **API 키**, 그리고 "오프라인일 땐 온디바이스, 온라인일 땐 클라우드로 향상"인지 "아예 클라우드로 전환(오프라인 포기)"인지 방향 결정 필요.

### 선택지 C — 이미지 전처리로 온디바이스 인식률 개선
대비/샤픈 보정, 자동 크롭 등. 무료지만 효과는 제한적(모델 자체 한계는 못 넘음), 구현 난이도 중간(현재 expo-image-manipulator는 crop/resize/rotate만 지원, 대비·샤픈은 별도 네이티브 코드 필요).

## 디자인 개선하려면 필요한 것

지금은 컬러/폰트/레이아웃 전부 기본값(React Native 기본 스타일, 파란 링크색, 시스템 폰트). 방향 잡으려면:
- 참고할 디자인(스크린샷, Figma, 다른 앱 레퍼런스) 있으면 공유
- 아니면 여행앱다운 톤(큰 글씨, 고대비, 원터치 강조) 기준으로 제가 잡아도 됨

## 참고 — 지금 사용 중인 것 / API 키 불필요

- Google ML Kit Text Recognition (Japanese) — 무료, 온디바이스, 키 불필요
- Google ML Kit Translate — 무료, 온디바이스(언어팩 다운로드 후), 키 불필요
- kuromoji-ipadic — 오픈소스 라이브러리, 키 불필요
- 위키백과 REST API (`ko.wikipedia.org/api/rest_v1/page/summary/...`) — 무료, 키 불필요, User-Agent 헤더만 필요
